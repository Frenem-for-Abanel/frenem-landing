<Tldr>

- Frenem runs on Django, PostgreSQL, and Next.js, chosen so that the stack is never the interesting part.
- The novelty budget goes to the domain: modelling organisations, computing diagnostics, and rendering structure people recognise.
- Every dependency has to earn its place twice: once when it is installed, and again the first time it misbehaves.

Frenem sells organisational clarity. It would be strange if the system behind
it were a puzzle. So the stack is deliberately unremarkable: Django for the
decision layer, PostgreSQL for the record, Next.js for the surface. Nothing in
that sentence will impress anyone at a conference, and that is the design goal.

## Where the novelty budget goes

Every product carries a fixed tolerance for the unproven. Spend it on an
exotic database and you have less left for the parts that are actually hard.
Our hard parts are domain problems: how to model an organisation without
flattening it into a tree, how to keep a diagnostic honest when anonymity
thresholds withhold data, how to draw a structure that a leadership team
recognises as their own. Those problems deserve the whole budget. The
framework underneath them should have had its surprises documented a decade
ago, by someone else.

## What each layer is for

Django is where decisions live: permissions, migrations, the admin, and the
object model that everything else defers to. It is boring precisely where
mistakes are expensive. PostgreSQL is the record. There is one database, it is
transactional, and no second store exists to drift out of agreement with it.
Next.js is the surface: static where a page can be static, server-rendered
where freshness matters, and never the layer where business rules hide.

The discipline that holds the three together is a readiness check that asks
one question per layer, answered before any deploy goes out:

```python
def readiness() -> dict[str, bool]:
    """A deploy that cannot answer all three does not ship."""
    return {
        "record": database.select_one(),
        "decisions": database.migrations_current(),
        "surface": frontend.build_matches_release(),
    }
```

## The cost we accept

Boring has a price and it is worth naming. We occasionally write code that a
newer framework would have generated, and we wait for features the ecosystem
has already celebrated elsewhere. That trade is deliberate: we give up some
convenience and get back predictability, upgrade paths measured in years, and
failure modes that are already described in someone else's post-mortem.

## What it buys

A quiet stack keeps the promises loud. When the tools underneath never demand
attention, every hour of attention goes to the product: sharper diagnostics,
clearer structure, better answers. Boring is not a compromise here. It is the
method.
